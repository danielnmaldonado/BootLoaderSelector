PURPOSE AND PLATFORM
--------------------
BootLoaderSelector is a single-threaded x64 UEFI application that discovers and
chainloads OpenCore and Clover. It uses UEFI Simple Text Output, not a desktop
windowing framework. It provides a scrolling selector, persistent settings,
hardware information, debug logging and GOP screenshots.

The release builder produces BootLoaderSelector.efi and a byte-identical
BOOTX64.efi. It writes build artifacts under Release/ and the canonical log
under BuildLogs/. It does not install the application on the host EFI partition
or modify host firmware settings or NVRAM.

QUICK START
-----------
1. Build from a clean checkout using the Linux or macOS instructions in README.md.
2. Launch BootLoaderSelector.efi from a UEFI shell or firmware boot menu on a
   test EFI volume. BOOTX64.efi is the alternative removable-media filename.
3. Select an entry with Up/Down and start it with Enter/Right. Options changes
   the timeout, remembered-selection behavior, hardware card and debug logging.

The selector scans EFI filesystem volumes for:
  \EFI\OC\OpenCore.efi
  \EFI\BOOT\OpenCore.efi
  \EFI\CLOVER\CLOVERX64.efi
  \EFI\BOOT\CLOVERX64.efi

It can also probe the configured preferred path. Entries on the selector's own
volume are prioritized. Yellow entries identify a USB device path. Filesystem
availability depends on the protocols and drivers provided by the firmware.

KEYBOARD
--------
Up / Down       Move the selection; compact lists scroll as needed.
Enter / Right   Boot the selected entry or open Options.
Esc / Left      Exit the selector or return to the previous screen.
F1              Show contextual help in the selector or Options.
Space           Show read-only details for a boot entry.
F5              Rescan EFI filesystem volumes.
F10             Save a screenshot when a usable GOP and volume are available.

In Options, Up/Down selects a setting and Left/Right changes it. Enter saves the
settings; Esc cancels edits. Home, End, Page Up and Page Down are not selector
commands. The runtime preserves the established shortcut behavior.

CONFIGURATION
-------------
Runtime settings are stored in \EFI\BOOT\BLS.plist. This is an XML plist
containing one dictionary with scalar strings, integers and booleans. It is not
one of the root source files named Config.plist, BootScan.plist, Ui.plist, etc.;
those files contain historical Clang analysis output, not runtime settings.

Key                       Type      Default
DefaultBootloader         string    OpenCore
DefaultPath               string    empty
DefaultVolumeLabel        string    empty
DefaultVolumeDevicePath   string    empty
Timeout                   integer   10 seconds; supported range 0..30
Debug                     boolean   false
ShowHardwareInfo          boolean   true
RememberLastSelected      boolean   true
HasRememberedSelection    boolean   false

Example initial configuration:

<?xml version="1.0" encoding="UTF-8"?>
<plist version="1.0">
<dict>
  <key>DefaultBootloader</key><string>OpenCore</string>
  <key>DefaultPath</key><string></string>
  <key>DefaultVolumeLabel</key><string></string>
  <key>DefaultVolumeDevicePath</key><string></string>
  <key>Timeout</key><integer>10</integer>
  <key>Debug</key><false/>
  <key>ShowHardwareInfo</key><true/>
  <key>RememberLastSelected</key><true/>
  <key>HasRememberedSelection</key><false/>
</dict>
</plist>

The application records the selected loader name, path, label and persistent
volume identity when remembering a selection. A stored strong device-path
identity must match; it never falls back to a label-only match. Remembered
autoboot requires a complete successful scan and exactly one global preferred
match. Missing, ambiguous or incomplete results keep the menu interactive.

For a valid remembered entry, a separate two-second startup window accepts an
arrow key to open the selector; otherwise the remembered entry launches. The
configurable menu countdown is distinct from that startup window. A returned or
failed child disables further automatic launches for that interaction.

The image volume is the preferred configuration volume. A malformed existing
BLS.plist is preserved: defaults apply in memory and automatic saves are
suppressed for that configuration. A valid final BLS.plist is authoritative.
BLS.tmp is used for staged writes and recovery, with bounded I/O, flush and
cleanup handling. Read failures and allocation failures are not silently treated
as a missing configuration. Screenshot destination selection is independent of
the handle authorized to save configuration.

The input limit is 64 KiB and XML nesting is limited to 32 levels. Known keys
with invalid values or duplicate occurrences are rejected. Text follows the
UEFI CHAR16/UCS-2 contract; unsupported supplementary characters and surrogate
code units are rejected by the configuration parser/writer. XML comments and
processing instructions preserve scalar character data when ignored.

DIAGNOSTICS AND HARDWARE INFORMATION
-----------------------------------
Debug=false is the default. When enabled, the runtime uses one log:
  \EFI\BOOT\BootLoaderSelector.log

The persistent log is bounded to 128 KiB. Writes and rollover handle errors
explicitly and retain recoverable buffered data; no periodic log timer or
additional rotated log files are created.

F10 saves 32-bit BMP files under:
  \EFI\BOOT\Screenshots\

Screenshot capture uses the console-associated GOP where it can be identified.
Ambiguous multi-GOP configurations are not resolved by blindly choosing the
first framebuffer. Capture requires available graphics and writable filesystem
services and reports a failure when those services are unavailable.

The hardware card reads available firmware/CPU information with bounded
SMBIOS, memory-map, PCI/GOP and topology handling. Firmware data is diagnostic;
this project does not implement an ACPI/AML interpreter.

BUILDING
--------
Linux x86-64 uses native GCC/G++, binutils, make, NASM, Python 3.10+, Clang/LLD,
OpenSSL, uuid-dev and sbsigntools. On Ubuntu:

  sudo apt-get install gcc g++ binutils make nasm python3 clang lld openssl uuid-dev sbsigntool
  ./Build-BootLoaderSelector-Release.command

macOS requires Xcode Command Line Tools, Python 3.10+, Java, Jsign, OpenSSL and
the original external Intel cross-toolchain. Set BLS_TOOLCHAIN_DIR to its
original directory, using a path without spaces or symbolic links. See
Toolchains/README.md. The exact 951-file catalog and hashes are verified before
any of those external tools run. The legacy binaries are not redistributed.

  BLS_TOOLCHAIN_DIR=/path/without/spaces/toolchain.gcc102.snb \
    ./Build-BootLoaderSelector-Release.command

Build-Debug-Full-Log.command requests additional diagnostics from the same
Release builder while it owns the build lock. Both entry points use:
  BuildLogs/BootLoaderSelector-Build.log

BLS_REVEAL_LOG=1 opts into revealing the log in Finder on macOS. Source and log
symlinks, multiply-linked logs, manifest mismatches and concurrent builds are
rejected. Release publication uses staging and rollback to preserve a previous
valid release if the new attempt fails or is cancelled.

SIGNING AND OUTPUTS
-------------------
The builder signs PE/COFF EFI executables using an ephemeral ad-hoc
RSA-3072/SHA-256 certificate and verifies them before publication. The private
key is temporary and is not included in the source or release. The public
certificate and build provenance accompany the output.

Supported signing routes include sbsign/sbverify and Jsign. The helper detects
Jsign capabilities and supports Jsign 7.x through extraction plus independent
Python/OpenSSL Authenticode verification. When needed, its official Jsign 7.5
bootstrap is hash-pinned and cached outside the source tree.

BLS_JSIGN_AUTO_DOWNLOAD=0 disables that bootstrap.
BLS_JSIGN_CACHE_DIR selects its cache directory.
BLS_JSIGN_JAR can identify a locally supplied Jsign JAR.

The signature proves integrity relative to the generated certificate. Secure
Boot additionally requires trust configured in the destination firmware. An
ad-hoc signature does not create that trust, and macOS Mach-O codesign is not a
PE/COFF EFI signing method. Independently rebuilt signed files can have different
hashes because each build creates a new key and certificate.

VERIFICATION AND SOURCE INTEGRITY
--------------------------------
Run the host/source checks without the final Release build:
  BLS_QUALITY_BUILD=0 ./AuditTests/Run-Release-Quality-Gate.command

Run the default repeated quality gate including the Release build:
  BLS_QUALITY_REPEAT=3 ./AuditTests/Run-Release-Quality-Gate.command

Signing tests need lld-link on PATH. On Homebrew, install lld@21 separately and
expose its bin directory; llvm@21 alone does not supply lld-link. Use OpenSSL
rather than the system LibreSSL on macOS. Unsupported sanitizer features are
reported as SKIP, not counted as successful coverage.

AuditReports/MANIFEST.sha256 covers immutable source, documentation and CI.
Generated build outputs, Git metadata and .DS_Store follow documented exclusion
rules. New or modified immutable files require a reviewed manifest update:
  python3 AuditTools/Update-Source-Manifest.py --write

Without --write, the tool verifies the manifest. The builder also checks the
exact immutable file set and refuses mismatches.

CI runs Linux/macOS quality gates, Linux Release compilation, macOS artifact
verification and a dedicated OVMF child-chainload smoke test. A version-matching
tag can publish the source/EFI ZIPs and checksums only after all five checks
pass. Repository, release and artifact access remain private.
